# Locked app focus

## Context

Noah confirmed that the tested window-drag gesture works and is not a blocker. He requested
investigation of app focus, foreground window order, and menu activation before polishing the service.
Keep the mini locked and retain vision, coordinate input, and generic window geometry routing.

## Decisions

- Noah requested public discussion and suggested menu activation may be a lower-priority edge case.
  Treat it as a known limitation to assess against actual workflows, not a universal impossibility.
  Terminal's menu previously worked while locked; switching menus to other tested apps did not.

- Distinguish a window accepting keys, an app's internal active state, the global foreground process,
  window order, and menu ownership. A successful activation return value does not establish any
  visible effect.
- Use isolated probes under the existing authorized Terminal context. Do not modify the installed
  service, use an accessibility tree, inject code into apps, or change security settings.
- Do not replace the displayed menu with different pixels until input to that menu also works.
  Displaying the right labels alone would conceal the remaining control problem.

## Verification

- All successful probe actions and captures passed both lock guards. The actual foreground process
  was PID 453, `/System/Library/CoreServices/loginwindow.app/Contents/MacOS/loginwindow`.
- `NSRunningApplication.activate` with all-windows and ignoring-other-apps returned true but left
  Calculator inactive according to `NSRunningApplication.isActive`. The compiler confirms that
  ignoring-other-apps has no effect starting with macOS 14.
- `SetFrontProcessWithOptions` returned 0 without changing the foreground app or captured menu.
- `_SLPSSetFrontProcessWithOptions` returned 0 with both mode 0 and mode 512. Calculator remained
  inactive in the global query. Mode 512 is `kCPSUserGenerated` in upstream yabai v7.1.15.
  Combining that call with the service's activation and key-window records in one GUI process
  did not open TextEdit's menu.
- `SLSSpaceSetFrontPSN` returned 0 for Calculator's desktop, Space 1. The lock screen remained
  foreground and the screenshot still showed Terminal's menu. No Space switch was performed.
- Earlier fixture logs show `NSApplication.isActive=true` inside the target app after synthetic
  activation, even though the global front-app query remains loginwindow. This is another reason
  not to conflate internal key focus with desktop menu ownership.
- A read-only `SLSGetProcessMenuBarWindowList` query returned the shared menu window 17 and status
  items for both Calculator and TextEdit. It did not identify their private menu backing windows.
- Full window metadata revealed offscreen 1920x24 windows owned by each app. Native captures of
  Calculator windows 1790/1793 show its real Calculator, Edit, View, Window, and Help labels.
  TextEdit windows 1464/1466 show TextEdit, File, Edit, Format, View, Window, and Help. Their companion
  windows are blank/transparent. These are real app pixels, not generated labels or AX data.
- Clicking the shared menu with the existing route did not open Calculator's menu. Neither did
  setting all event-window fields to zero, targeting the private menu window directly, or using
  event window 0 with its private menu ID in the pointer fields. Both Calculator menu variants
  and TextEdit's menu backing were tested.
- Removing shared global mouse-button events for menu clicks did not fix it. A full transition
  deactivated Terminal, Calculator, and TextEdit through user-app records, then activated TextEdit.
  Menu tests still failed with and without shared button state. No records targeted loginwindow.
- Post-click metadata showed no new TextEdit popup window, including offscreen windows. Thus this
  tested failure is not merely the screenshot filter hiding a successfully opened menu.
- Command-Shift-/ did not visibly open Help in Calculator or TextEdit. Targeted Control-F2 with
  the function-key flag did not visibly focus TextEdit's menu bar.
- The stable service continued to select the intended app windows through coordinate clicks.
  The existing proof's window movement and key-input results are unchanged.

## Follow-ups

- Menu activation is unresolved. The tested public and native activation requests are insufficient
  while the lock screen owns the global foreground. This does not prove every possible route fails.
- Investigate how an inactive app's menu tracking is entered before changing capture or shipping a
  focus API. Any solution must preserve the lock screen and verify real menu commands across apps.
- The independently named app and its permissions remain a separate packaging task. A new app
  identity has not been shown to change the focus behavior described here.

### Public discussion checked on November 6, 2026

- [Keyboard Maestro activation failure, 2015 with 2017 follow-up](https://forum.keyboardmaestro.com/t/script-fails-when-screen-is-is-locked/1073)
  reports Activate OmniFocus timing out while locked, also reproduced with another app. The developer
  distinguishes launching an app from activating it. This is a close analogue for activation failure,
  not proof of our precise menu-routing limitation.
- [Keyboard Maestro / Moom discussion, January 2026](https://forum.keyboardmaestro.com/t/wake-screen-actions-and-passwords/51007)
  reports a locked screen preventing window-layout automation. It is adjacent evidence, not a
  menu-specific finding or a reason to discard our working window routing.
- [Apple WWDC23 AppKit activation](https://developer.apple.com/videos/play/wwdc2023/10054/)
  says activation is a request evaluated in context and ignoringOtherApps no longer forces it.
  The explanation is not specific to a locked screen.
- [CUA lock-screen discussion, May 2026](https://github.com/trycua/cua/issues/1744)
  discusses loginwindow and proposes an opt-in unlock integration. This concerns access to the
  protected lock screen, not proof that background app menus are universally inaccessible.
- No exact public reproduction of our combination of working background window input and failed
  cross-app menu switching was found in this search. Broad statements that all GUI automation fails
  while locked do not override our observed successful input, capture, and Terminal-menu tests.
