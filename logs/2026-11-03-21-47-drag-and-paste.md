# Drag diagnosis and bulk text proof

## Context

Noah asked to continue until input works more broadly. He also requires bulk text insertion
without a separate delayed keystroke for every character. The mini must remain locked.

## Decisions

- Continue with small generic input proofs, screenshots, and window geometry. No accessibility tree.
- Test clipboard paste with a single keyboard shortcut. Preserve the existing clipboard.
- Use an instrumented scratch app with standard controls to observe delivery, not to implement
  special drag or paste handling. Keep all input decisions based on screenshots.

## Changes

- Started a fresh drag and bulk text experiment.
- Added paste with clipboard preservation and fixed-count Command-A/Command-V events.
- Added a target-only window focus experiment using SLPSPostEventRecordTo. It sends no defocus
  event to loginwindow and does not request an unlock or change security settings.

## Verification

- SSH connected without authentication prompts. Both mini lock flags were true.
- Initial paste reached the scratch window's key-event handler but changed no text. TextEdit
  also saved zero bytes after the same paste shortcut. These attempts failed.
- All three target-only focus records returned status zero. After focus delivery, TextEdit
  displayed the pasted 29-character text and Command-S saved all 29 bytes.
- Repeated with 82,000 characters / 108,000 UTF-8 bytes across 2,000 lines, including Japanese,
  emoji, accents, a combining accent, tabs, and newlines. The saved SHA-256 matched the source:
  `dc17d41948a6ea79d648dd351da8aaf2424248e0de3fba6d0de00e7122da987c`.
  Clipboard setup and shortcut dispatch took 0.220 seconds for 29 characters and 0.215 seconds
  for 82,000 characters. These are dispatch timings, not total render or save latency.
  Clipboard restoration ran after both pastes.
- Target focus changed Terminal's title buttons to active, but its title drag still failed.
  Both console lock flags remained true. Keyboard focus alone does not solve native title dragging.
- Mouse dragging selected `beta` in TextEdit. Pasting `BETA` without Select All changed only that
  word; Command-S saved exactly the expected three-line document.
- Public process-targeted pixel scroll did not move TextEdit. SkyLight-targeted line scrolling
  with an explicit window location moved the visible document from line 1971 to line 1963.
- Annotated, session, and HID global event routes did not move Terminal's title bar.
- A shell printf interpreted JSON newline escapes in one preparation command, causing a JSON
  decode error and stopping that probe. Corrected command delivery to preserve literal JSON
  and rename a complete temporary file into place. The replacement probe completed the test.
- SLSDragWindowRelativeToMouse is exported on the mini. Its first bounded test returned zero but
  did not move TextEdit. A zero return code alone is not proof of dragging.

## Follow-ups

- Continue native title-drag investigation and test independence from the SSH connection.
