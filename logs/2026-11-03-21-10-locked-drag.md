# Locked drag proof

## Context

Noah requires dragging on the locked Mac mini. Generic routed clicks and typing already work.
The existing title-bar drag produced no movement. Keep the console locked and use only images,
window geometry, and mouse/keyboard events. No accessibility tree or app-specific control.

## Decisions

- Separate dragging inside an app from moving a window by its title bar.
- Test missing mouse movement deltas and button event numbers before adding other mechanisms.
- Keep experiments in a fresh scratch directory. Preserve the working click/type proof.

## Changes

- Saved the bounded drag experiment and standard-control fixture in `probes/locked-drag/`.
- Updated the root and click/type proof documentation with the measured drag support and limits.

## Verification

- SSH connected. Both mini lock flags were true before this work.
- Added deltas and a shared button event number. Title movement and text selection still failed.
- A scratch AppKit app with a standard NSSlider logged received events. Coordinates and dragged
  event types were correct. Without shared button state, events stayed in the default run-loop
  mode and the slider did not move. With a global session button-down held during the routed
  drag, the receiver entered NSEventTrackingRunLoopMode and its slider moved from x1500 to x1630.
  This is a verified app-control drag, not window movement. No custom drag handler was added.
- Title dragging still failed with shared button state, mirrored global pointer motion, the
  annotated event route, and a normal NSRunningApplication activation request. Activation
  returned true but isActive stayed false. No lock setting changed.
- Matching the observed global button event number, zero, and setting HID button state also
  left the title position unchanged. Both button states returned false after release.
- One motion script failed initially because the mini's existing Python is 3.9 and does not
  support match syntax. Replaced that dispatch with explicit if/elif/else and reran successfully.
- An alternate route using SLEventPostToPid and CGEventSetWindowLocation moved Messages by its
  title bar repeatedly while locked. The first receiver fixture had expired before this test;
  coordinate selection correctly picked Messages, not the expired fixture. Recorded window
  positions were (872,344), (896,444), (881,344), and (781,444). The third drag moved exactly
  (-100,+100). A final drag restored the original position. Images confirmed the movement.
- This route required shared button-down state but did not require mirrored global motion.
  A control attempt without shared button state left Messages unchanged.
- The same route failed to move Terminal and a fresh standard AppKit fixture by their titles.
  Therefore the broad dragging requirement remains unmet; do not report universal support.
- A fresh standard-slider test using this route moved its thumb from (1630,514) to (1595,514).
  The image and receiver's NSEventTrackingRunLoopMode log both confirmed the drag.
- The first alternate-route attempt failed to resolve CGEventSetWindowLocation using a bundle
  lookup. Global release still ran. Resolving exported symbols from the process table fixed
  the lookup; the successful run used a new command prefix to avoid replaying commands.
- The bounded probe stopped. The fresh fixture process was identified and terminated. Shared
  button state was released after gestures; both lock flags remained true. No security setting
  changed, and no new Tailscale authentication or permission request was needed.

## Follow-ups

- Determine why standard title bars reject events that work for Messages and standard sliders.
  No app-specific workaround or window-position setter has been added.
- File drag-and-drop, text selection, other controls, and long-run reliability remain unproven.
  The successful alternate route uses undocumented macOS APIs.
